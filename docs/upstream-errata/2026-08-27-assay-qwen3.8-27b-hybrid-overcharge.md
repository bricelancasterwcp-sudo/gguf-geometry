# Upstream erratum — assay's published `qwen3.8:27b` KV geometry

Date filed: 2026-08-27
Filed by: gguf-geometry Task 4 (v1 seed corpus), recorded here because
this repo cannot write to assay.
Status: **open** — filed against assay, not yet corrected upstream.
Effect on this repo: `qwen3.8-27b` is **withheld** from `vectors/v1/`.

## Summary

assay publishes `qwen3.8:27b` at **260 KiB/token** of KV cache. That
figure charges all 65 raw blocks as attention layers. The model's own
metadata states `full_attention_interval: 4` and
`nextn_predict_layers: 1`, so SPEC.md R6 and R3 give **16** attention
layers, not 65 — the published number over-charges the attention term by
**4.0625x**. The same metadata states a full `ssm.*` set, so SPEC.md R4's
`recurrent_state_bytes` term applies and is absent from every published
figure.

This is the same defect class SPEC.md R3 was written against (bloomery
turn 5: all-40-blocks charged on Qwen3.6-35B-A3B, 10 real attention
layers). assay's E1 erratum corrected this model's `head_dim`; it did not
touch its layer count, so the corrected row carries a second, unreported
defect on top of the E1 correction.

## The contradiction, in full

Published: `260 KiB/token = 266240 bytes`, and

```
266240 == 2 * 65 * 4 * 256 * 2
          |    |   |   |     |
          K,V  |   |   |     bytes_per_element (f16)
               |   |   head_dim (key_length, R1 — correct)
               |   head_count_kv
               block_count, charged raw
```

SPEC.md on the same metadata:

- **R6** — `serving_block_count = block_count - mtp_num_hidden_layers`.
  SPEC.md names the key `mtp_num_hidden_layers`; `nextn_predict_layers`
  is the same concept under this architecture's spelling, so
  `serving_block_count = 65 - 1 = 64`. (Reading the key names strictly
  instead — no R6 term — changes the count but not the finding: R3 alone
  already forbids charging the raw block count, and `65 / 4` is not
  integral, which is itself a signal that the raw count is the wrong
  input.)
- **R3** — `attention_layer_count = serving_block_count /
  full_attention_interval = 64 / 4 = 16`. "Never the raw block count."
- **R4** — the `ssm.*` keys mean a distinct `recurrent_state_bytes` term
  is charged per context. "Zero ONLY when the architecture has no
  recurrent layers — never as a default."

65 charged attention layers against 16 allowed is a **4.0625x**
over-charge, and no published figure carries R4's term at all.

**Non-adoption clause.** The attention term a conforming implementation
would produce on these keys (`2 * 16 * 4 * 256 * 2`) is arithmetic shown
here to size the contradiction — it is **not** a value this repo may
pin. It is unmeasured, it has no published evidence behind it, and its
R4 companion term is unknown. Nothing in `vectors/` may carry it, and no
tool in this repo derives it. (Design spec section 0: this repo contains
no geometry implementation.)

## Why the vector is withheld rather than authored

The task brief listed `qwen3.8-27b` as a load-bearing v1 vector with
`expected.kv_bytes_per_token` = the errata's corrected value. Pinning
266240 as `expected` would make the conformance corpus *require* every
consumer to reproduce this over-charge — freezing, as the contract, the
exact defect the contract exists to catch. SPEC.md is the binding
authority on conflicts, so that option is not available; deriving the
conforming value here is banned twice over (no implementation, never
invent a value). Design spec section 4 gives the remaining path: *"If a
desired case has no committed evidence, it waits for a later set rather
than entering as an unverified number."*

`tests/test_v1_vectors.py::test_qwen38_27b_is_deliberately_absent` pins
the omission so nobody adds it back at 260 KiB by default, and
`test_withheld_ids_are_documented` pins this file as its record.

## What closes this

Either of:

1. **A conforming measurement.** A live run that charges R3/R4/R6
   correctly on this model and publishes kv, `attention_layers`,
   `serving_block_count` and `recurrent_state_bytes` with a transcript.
   Requires GPU time — out of scope for this repo, which measures
   nothing.
2. **An upstream correction in assay** — an erratum row against the
   `tier-enthusiast-2026-08` profile and a rebuild of the matrix, after
   which the corrected values are citable evidence here.

Until then the case is a **scope reduction** of v1, ruled and recorded,
not an oversight. If the correction lands before this repo's publish
gate the vector may still enter v1; after publication SPEC.md's
versioning rule applies and it enters a later set instead (old sets are
never edited).

## Coverage consequence

With this case withheld, `vectors/v1` as of the E1 corpus exercises
**R1, R2, R5, R7 and R8** but not **R3, R4 or R6**. The plan's next task
(REAP-48 hybrid + mtp trap, both with published hardware-verified
bloomery values) covers all three, so the gap is closed inside v1 by a
case whose numbers *are* evidenced.
